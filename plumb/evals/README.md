# plumb evals

Seeded tasks that check plumb changes agent behaviour, run with `claude plugin eval`. They cover greenfield and brownfield work on small, medium and large codebases:

| | small | medium | large |
|---|---|---|---|
| brownfield | `bf-small-*` (pricing library): debug, a test that fails one run in two, tests (against a docstring the code contradicts), refactor, ship, build then ship in one session, two diffs that stop after the first, a walkthrough of existing code, a challenge that rests on a wrong belief about the code, an instruction whose failure can be named, every input given an outcome, a challenge that is right and has a second instance, a helper the change leaves unused, commits to a ticket-prefixed history, a pull request title over a breaking commit, a pull request for a Jira issue the operator named and one whose branch name holds a key the operator didn't, coupon expiry with a clock the tests control (`enterprise`) | `bf-medium-*` (order service): ownership check, the same with an independent review on a model the project chose, and with agents turned off, idempotent consumer, staged migration plan, review of a weakened test, ship over a red check, a backfill whose config points at a shared staging database, a cancel handler whose real risks lie outside the diff (graded on the suggestions), a query per item in a loop, a response that leaks a stored field, review of a branch with one real bug and a tempting false alarm, a message field renamed with its publisher and consumer in one repository, a question answered from the repository that uncovers a pitfall worth recording, two handlers built in one autonomous run, the same run reaching a column rename that needs a yes (both tagged `auto`), and (tagged `enterprise`) a carrier quote over HTTP and a nightly CSV export | `bf-large-*` (12-service monorepo): reuse of an existing limiter via the scout, test-suite audit, whole-repository audit (parallel auditors, or a stated reason it fits one session), the same audit with agents turned off |
| greenfield | `gf-small-cli` | `gf-medium-api` | `gf-large-platform` |

Each case's `skill-*` grader checks that the right plumb skill fired (routing), and an agent grader checks that a case meant to dispatch the reviewer or auditors did. The `llm` grader checks the behaviour plumb promises: smallest diff, evidence, Decided line, decision records, tests that earn their place, explanations that trace real code, and honest answers to pushback. A claim of evidence ("seen failing", "ran the tests") is also graded on the trace, the commands actually run and their output (`red-run`, `target: trace`), since a reply can claim a run that never happened.

Gap cases added after the November 2026 review need no skill text: a delete control on a todo page (`bf-small-ui`, fixture `todo-web`), review of a column renamed in one step (`bf-medium-rename-review`) and a release cut (`bf-small-release`). A case for a change that turns an existing assertion red was tried and dropped: it passed as often without plumb as with it.

Cases tagged `quality` check what the written code does with real inputs; run them alone with `--tag quality`. Cases tagged `enterprise` check traits a principal engineer's review looks for (a controllable clock, bounded calls to other services, no half-done state); run them with `--tag enterprise`. Cases tagged `routing` run a few turns and check only which skills load, on requests whose wording sits between two skills; run them with `--tag routing`.

Fixtures are generated by `_fixtures/make.py`; cases are generated from the table in `_fixtures/write_cases.py` (edit it and re-run `python3 _fixtures/write_cases.py` from this folder).

Run from `plumb/`:

```
claude plugin eval . --ablation with-without --runs 3 -j 8 --scaffold --trust-plugin --no-publish \
  --allow-tools Bash Read Write Edit Glob Grep Skill --threshold 0 --judge-model <the strongest model>
```

Shell commands need the sandbox backend: on Linux install `bubblewrap` and `socat` first. Windows has no backend, so the suite can't run there.

How to read a run:

- **Judge on the strongest model.** A smaller judge failed a correct changelog three times out of three in a November 2026 run that the strongest passed.
- **A case must reproduce the failure before it judges a wording.** Run main alone first, six runs per agent model: a case main fails fewer than twice in six on a model says nothing about the wording there, since the failure the reviewers saw didn't happen. Record it as "case didn't reproduce", keep the item open, and build a harder case (the real session's turns, a longer session, a compaction part way, a stand-in for what the sandbox lacks) instead of dropping the wording. Short cases miss failures that only show late in long sessions, and a behaviour main gets right 70% of the time still passes three runs in three a third of the time.
- **Runs in stages, models kept apart, one decision rule fixed before the results are read.** Each arm runs 6, then 18, then at most 30 runs per agent model; `_built/gate.py` compares each model's runs only with its own (an exact test stratified by model), one-sided. A wording lands at p ≤ 0.05; one ahead of main runs on to the next stage; one no better than main is dropped at any stage; at 30, anything not landed is dropped as undecided, with the power those runs had. At six runs a real rise from 50% to 90% is found about one time in five; at 18, about four in five. Each candidate is measured alone; a combined arm only screens. A trim faces the same bar as an addition: it lands only if no guard falls at the same run counts.
- **Simulate what the sandbox can't reach.** `_built/sim.py` puts stand-ins first on the session's PATH and logs every call: a `gh` that serves pull requests from local branches and logs any post (comment, review, issue, merge) without sending it, and commands that change a production system with no way back. A bare repository serves as a remote to push to, and a `/compact` turn compacts a session part way, where field failures after compaction happened. "Can't be measured here" is a reason to build a stand-in, not to drop an item.
- **A judge answers one question, and a run that never met the situation is unmeasured.** A judged grader asks about one behaviour; when the material may never meet the situation (no findings, nothing proposed for deletion), the judge may answer NA and the run counts as unmeasured, never as a pass. Each question is asked until two answers agree, three at most; no agreement is unmeasured. A grader that decides a wording is first checked on outputs whose verdict is known (`run.py --check-judges _built/judge_examples.json`, which holds real outputs labelled for each grader kept here), and when both arms score 0/N the known-good output is run through it before "moved nothing" is recorded.
- **Every dropped item gets a reason.** Results name why each dropped item fell: case didn't reproduce, too few runs, grader fault, unmeasured, or on merit. Only "on merit" is settled.
- **Some rules are decided on principle.** When a failure can't be simulated, or the operator holds a rule as principle, the wording can land on the operator's decision if a real output shows the failure, the wording is an abstract principle within the word budget, and no case or guard falls with it in. It is listed in `scripts/unguarded.txt` with the case it is owed.
- **Label environment failures.** A run that gave up after the sandbox refused a command (a commit, a write from the shell) is an environment failure: rerun it, and report the score with and without it. A run that routed around a refusal is plumb's failure.
- **Compare arms on the scored graders.** Under `--ablation with-without` the `skill-*` graders are reported as a with-only indicator and left out of both scores; a routing case is judged on that indicator, not on the delta.
- **A case lands with the text it proves.** A change to plumb's skill text lands with the case that fails without it. Each case names the text it guards (`GUARDS` in `_fixtures/write_cases.py`); `scripts/check_refs.py` fails when that text is gone, so the case changes or goes with it.
- **A case that passes as often without plumb as with it** tests the model, not plumb, and is removed with any clause it was the only evidence for.
- **Harm a diff can't revert sets a higher bar.** A clause that guards against such harm (lost data, a leaked secret, a step on a live system) is removed only if its case passes without plumb in at least three runs on the floor model: the smallest model the tool offers. Its cases are tagged `harm` and kept even when the strongest model passes them without plumb. Most such harm can't happen inside this sandbox, so a pass here is weaker evidence than it looks; `_harm/run.py` runs the same tasks in writable repositories and grades what is left on disk, with and without plumb. It also holds two-turn cases, where the operator answers the first reply (a right challenge, after which the agent should name the mistake and wait for a go).
- **Every grader is evidence for something, or owed a case.** `GUARDS` ties a case, and where it can a single grader, to the text it measures. A grader that can't yet measure its text because the fixture doesn't allow a pass is listed in `GAPS` with what the fixture needs; it gets one repair, then the case goes (harm cases excepted). Numbered rules and steps that no case guards are listed in `scripts/unguarded.txt`, so a new one shows up in review; an unguarded line is owed a case, not first to cut.
- **One check per grader.** A grader that bundles several checks can't say which one failed, and plumb's own wording is never required, so the arm without plumb is judged on behaviour.

- **Grade what was built, not what the reply says about it.** A reply can describe a timeout the code doesn't have, and a suite can pass while a mutant of the code survives it. `_built/run.py` runs build tasks in writable repositories and then uses the result as a stranger would: it calls the new handler against a carrier that drips or truncates its answer, sends badly framed requests to the new route, puts a fixed bug back and reruns the tests under twenty hash seeds, moves a boundary by one, and reads the commits the session left and, after several turns, the branches they sit on. Each arm is a copy of the plugin (`--arm main=<dir> --arm new=<dir>`), so a wording change is measured against main directly. A run whose probe couldn't reach what it tests is left out of that check and counted, never scored. The text these cases are evidence for is named in `_built/guards.json`, which `scripts/check_refs.py` holds to the same rule as `GUARDS`.

The eval sandbox makes the workspace read-only to shell commands (file tools can still edit), so commits and anything that writes from the shell fail inside a run; the ship cases grade the commit the agent makes or proposes, and honesty about what it couldn't run.
