# plumb evals

Seeded tasks that check plumb changes agent behaviour, run with `claude plugin eval`. They cover greenfield and brownfield work on small, medium and large codebases:

| | small | medium | large |
|---|---|---|---|
| brownfield | `bf-small-*` (pricing library): debug, a test that fails one run in two, tests (against a docstring the code contradicts), refactor, ship, build then ship in one session, two diffs that stop after the first, a walkthrough of existing code, a challenge that rests on a wrong belief about the code, an instruction whose failure can be named, every input given an outcome, a challenge that is right and has a second instance, a helper the change leaves unused, commits to a ticket-prefixed history, a pull request title over a breaking commit, coupon expiry with a clock the tests control (`enterprise`) | `bf-medium-*` (order service): ownership check, the same with an independent review on a model the project chose, and with agents turned off, idempotent consumer, staged migration plan, review of a weakened test, ship over a red check, a backfill whose config points at a shared staging database, a cancel handler whose real risks lie outside the diff (graded on the suggestions), a query per item in a loop, a response that leaks a stored field, review of a branch with one real bug and a tempting false alarm, a message field renamed with its publisher and consumer in one repository, two handlers built in one autonomous run, the same run reaching a column rename that needs a yes (both tagged `auto`), and (tagged `enterprise`) a carrier quote over HTTP and a nightly CSV export | `bf-large-*` (12-service monorepo): reuse of an existing limiter via the scout, test-suite audit, whole-repository audit (parallel auditors, or a stated reason it fits one session), the same audit with agents turned off |
| greenfield | `gf-small-cli` | `gf-medium-api` | `gf-large-platform` |

Each case's `skill-*` grader checks that the right plumb skill fired (routing), and an agent grader checks that a case meant to dispatch the reviewer or auditors did. The `llm` grader checks the behaviour plumb promises: smallest diff, evidence, Decided line, decision records, tests that earn their place, explanations that trace real code, and honest answers to pushback. A claim of evidence ("seen failing", "ran the tests") is also graded on the trace, the commands actually run and their output (`red-run`, `target: trace`), since a reply can claim a run that never happened.

Gap cases added after the November 2026 review need no skill text: a delete control on a todo page (`bf-small-ui`, fixture `todo-web`), review of a column renamed in one step (`bf-medium-rename-review`) and a release cut (`bf-small-release`). A case for a change that turns an existing assertion red was tried and dropped: it passed as often without plumb as with it.

Cases tagged `quality` check what the written code does with real inputs; run them alone with `--tag quality`. Cases tagged `enterprise` check traits a principal engineer's review looks for (a controllable clock, bounded calls to other services, no half-done state); run them with `--tag enterprise`. Cases tagged `routing` run a few turns and check only which skills load, on requests whose wording sits between two skills; run them with `--tag routing`.

Fixtures are generated by `_fixtures/make.py`; cases are generated from the table in `_fixtures/write_cases.py` (edit it and re-run `python3 _fixtures/write_cases.py` from this folder).

Run from `plumb/`:

```
claude plugin eval . --ablation with-without --runs 3 -j 8 --scaffold --trust-plugin --no-publish \
  --allow-tools Bash Read Write Edit Glob Grep Skill --threshold 0 --judge-model claude-opus-5-5
```

Shell commands need the sandbox backend: on Linux install `bubblewrap` and `socat` first. Windows has no backend, so the suite can't run there.

How to read a run:

- **Judge on the strongest model.** A smaller judge failed a correct changelog three times out of three in a November 2026 run that the strongest passed.
- **Three runs per arm.** One run sits inside the noise between runs (about ±0.1 on the suite), so no keep-or-cut decision rests on it.
- **Compare arms on the scored graders.** Under `--ablation with-without` the `skill-*` graders are reported as a with-only indicator and left out of both scores; a routing case is judged on that indicator, not on the delta.
- **A case lands with the text it proves.** A change to plumb's skill text lands with the case that fails without it. Each case names the text it guards (`GUARDS` in `_fixtures/write_cases.py`); `scripts/check_refs.py` fails when that text is gone, so the case changes or goes with it.
- **A case that passes as often without plumb as with it** tests the model, not plumb, and is removed with any clause it was the only evidence for.
- **Harm a diff can't revert sets a higher bar.** A clause that guards against such harm (lost data, a leaked secret, a step on a live system) is removed only if its case passes without plumb in at least three runs on the weakest model plumb supports. Most such harm can't happen inside this sandbox, so a pass here is weaker evidence than it looks.

The eval sandbox makes the workspace read-only to shell commands (file tools can still edit), so commits and anything that writes from the shell fail inside a run; the ship cases grade the commit the agent makes or proposes, and honesty about what it couldn't run.
